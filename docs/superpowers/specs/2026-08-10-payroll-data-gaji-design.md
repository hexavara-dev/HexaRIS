# Data Gaji (Payroll) — Design

**Date:** 2026-08-10
**Module:** `Payroll` (new bounded context)
**Status:** Approved, ready for planning
**Scope:** Frontend only, same shape as `Employee`: no DB migrations, no mutating HTTP routes.
Every payroll record is a dummy seed dataset overlaid with `localStorage` edits, so the page
"works" (persists across refresh) without a real backend. Only the list + detail/edit dialog for
**Data Gaji** are built. `Pengaturan Gaji` and `Reimburse` (also present in the sidebar/screenshots)
stay unbuilt — their nav links are already wired but out of scope for this pass.

## Problem

The sidebar already has a `Penggajian → Data Gaji` entry (`/payroll/data`, icons already committed)
but no module/route/page exists behind it — the link currently 404s. The user supplied 4 reference
screenshots (list page, view-mode detail dialog, edit-mode detail dialog, post-save toast) plus the
exact JSX markup for the list page. Two design-system components already partially match the
screenshots (`card/kpi-stat.tsx`'s `ActiveEmployeesKpiCardDemo`/`PayrollStatusKpiCardDemo`, and
`pop-up/dialog-salary-detail.tsx`'s `DialogSalaryDetail`) but neither is wired to real data or a
route yet, and `DialogSalaryDetail` is view-only (no edit mode).

## Module scaffold

New `app/Modules/Payroll/` context, alias `payroll`, following `Employee`'s exact precedent (no
migrations, no store/update routes — everything mutating happens client-side):

```
app/Modules/Payroll/
  module.json                                  # alias: payroll
  permissions.php                               # ['payroll.viewAny', 'payroll.update']
  routes/web.php                                 # GET /payroll/data -> payroll.data.index, can:payroll.viewAny
  Providers/PayrollServiceProvider.php
  Http/Controllers/PayrollController.php         # index() only -> Inertia::render('Payroll::pages/Index')
  resources/js/pages/Index.tsx
  resources/js/pages/columns.tsx
  resources/js/components/payroll-detail-dialog.tsx
  resources/js/lib/payroll-storage.ts
```

`payroll.update` is declared (matching `Employee`'s declared-but-unused `create`/`update`/`delete`
precedent) but nothing server-side actually gates on it — there is no update route to gate, exactly
like Employee's wizard.

## Data model (dummy, deterministic)

New top-level seed data, sibling to `resources/js/data/Employee/`:

```
resources/js/data/Payroll/
  branch.ts           # 3 dummy branches: Jakarta, Bandung, Surabaya
  period.ts            # 3 periods: 2026-05, 2026-06, 2026-07 ("Mei 2026" … "Juli 2026 (Bulan ini)")
  payrollEntry.ts       # 20 employees x 3 periods = 60 generated entries
```

- **Branch assignment** is derived from each seed employee's index (`employee.findIndex(...) % 3`)
  computed inside `payrollEntry.ts` — the `Employee` module's own files are not touched.
- **`PayrollEntry`** fields: `id`, `employee_id`, `period` (`YYYY-MM`), `branch_id`, `base_salary`
  (pulled from `employeeCompensation.ts`, not duplicated), `earnings: { position_allowance,
  meal_allowance, transport_allowance, overtime }`, `deductions: { alpha, late, bpjs_health,
  bpjs_employment, pph21 }`, `status: 'selesai' | 'proses' | 'belum'`, `payment_date: string | null`,
  `payment_method: string | null`.
- Amounts are generated by a **pure, seeded function of employee index + period index** (percentages
  of `base_salary` plus small index-based variation) — no `Math.random()`, so the array is stable
  and reviewable, computed once at module load.
- Derived per row: `totalEarnings = base_salary + sum(earnings)`, `totalDeductions =
  sum(deductions)`, `thp = totalEarnings - totalDeductions`.

### Persistence (`lib/payroll-storage.ts`)

Mirrors `employee-storage.ts`'s overrides half exactly (no "local new record" half needed — this
pass never creates new payroll rows, only edits existing seed ones):

```ts
const STORAGE_KEY = 'hexaris.payroll.overrides'; // Record<entryId, Partial<PayrollEntry>>
loadPayrollOverrides(): Record<string, Partial<PayrollEntry>>
savePayrollOverride(id: string, patch: Partial<PayrollEntry>): Record<string, Partial<PayrollEntry>>
```

`Index.tsx` merges `payrollEntry.map(e => ({ ...e, ...overrides[e.id] }))` at render, same pattern
`Index.tsx` (Employee) already uses for `overrides`.

## Components

### List page — `Payroll::pages/Index`

`AppLayout` + toolbar (`DataTable`'s built-in `search` + two `filters`: Cabang [select over the 3
dummy branches], Periode [select over the 3 dummy periods, default = latest/"bulan ini"]) + 3×
`KpiStatCard` (`@/components/design-system/card/kpi-stat.tsx`, reused as-is — its two existing icon
functions, `ActiveEmployeesIcon` and `PayrollStatusIcon`, get `export`ed so they're reusable instead
of re-drawn; a third `TotalSalaryIcon` is added the same way) computed from the currently filtered
rows:

1. Total Semua Karyawan Aktif — distinct `employee_id` count for the selected period/branch.
2. Total Semua Gaji Yang Harus Dibayar — `sum(thp)` for the selected period/branch, formatted IDR.
3. Status Pembayaran Gaji — count of `selesai` vs `belum` (rows where `proses` exist are counted
   into neither big number, matching the screenshot's two-value summary; `proses` is still a valid
   per-row status shown in the table/dropdown).

`DataTable` (`variant="design-system"`, client mode, `data` = merged+filtered entries joined with
employee name/position/branch) with columns: ID (`employee_number`), Karyawan (name + position, two
lines), Gaji Pokok, Tunjangan (`sum(earnings.*allowance*)`, green), Lembur (green), Potongan (red),
THP, Status. Status cell is an inline `Select`-style dropdown (Selesai/Proses/Belum, colored per
value) that writes straight to `payroll-storage.ts` on change — no dialog needed for a pure status
flip, matching the chevron-button affordance in the reference markup. A trailing Aksi column has one
icon button (pencil) that opens the detail dialog.

### Detail/Edit dialog — `payroll-detail-dialog.tsx`

Wraps the existing `DialogSalaryDetail` visual language but adds `mode: 'view' | 'edit'`:

- **View mode** (screenshot 2): renders exactly like today's `DialogSalaryDetail` — read-only
  `SalarySection` rows, `Periode`/`Status`/`Tanggal Bayar`/`Metode Bayar` shown as
  non-editable pill buttons, footer = "Edit Slip Gaji" + "Cetak Slip Gaji" ("Cetak" opens
  `window.print()` on the dialog content — no real PDF generation, out of scope).
- **Edit mode** (screenshot 3): the four header fields become real controls (`Select` for
  Periode/Status/Metode Bayar, a date input for Tanggal Bayar) and every earnings/deductions row
  becomes a `Rupiah`-formatted `Input`; footer becomes a single full-width "Simpan" button.
- Opening the dialog (pencil icon in the table) starts in **view** mode, pre-filled with the row's
  real current values — the screenshots' edit-mode "Pilih"/empty placeholders are treated as an
  artifact of how that particular mock frame was captured, not an intentional reset-on-edit
  behavior; edit mode always starts from the current values for usable UX.
- **Simpan** writes the edited fields via `savePayrollOverride(entry.id, patch)`, fires
  `toast.success('Berhasil Disimpan')` (`sonner`, same as Employee), and returns the dialog to view
  mode showing the freshly saved numbers (does not close the dialog — the toast in screenshot 4
  appears while the dialog is still open).

## Edge cases

- A seed employee with no `employeeCompensation` row for a given period doesn't exist in this
  dataset — `payrollEntry.ts` only generates rows for employees that have a compensation record,
  so this can't happen by construction.
- Switching the Periode filter changes which period's rows are visible/summed; switching Cabang
  narrows further. Both compose (AND), same as `DataTable`'s existing `filters` semantics.
- `localStorage` unavailable/throws (private browsing quota, etc.): `loadPayrollOverrides` catches
  and returns `{}` (same defensive pattern as `loadEmployeeOverrides`), so the page still renders
  seed data even if persistence silently fails.
- Editing a field to a non-numeric value: the Rupiah `Input` strips non-digits on change (same
  approach as existing Rupiah-formatted inputs in the Employee financial step), so it can't be
  saved as `NaN`.

## Out of scope (this pass)

- `Pengaturan Gaji` and `Reimburse` pages — nav links stay as-is (not yet built, not stubbed).
- Any real backend: no migration, no store/update route, no permission actually gating a mutation
  (only `payroll.viewAny` gates the index route).
- Real PDF export for "Cetak Slip Gaji" — `window.print()` only.
- Adding/deleting payroll rows — only editing an existing generated row.
